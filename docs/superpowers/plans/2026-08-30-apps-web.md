# Plan de implementación — `apps/web`, lado paciente

> **Para agentes:** SUB-SKILL REQUERIDA: usar `superpowers:subagent-driven-development`
> (recomendado) o `superpowers:executing-plans` para implementar tarea por tarea.
> Los pasos usan checkbox (`- [ ]`) para el seguimiento.

**Objetivo:** que alguien sin cuenta pueda buscar un profesional, ver sus
horarios reales y reservar uno, creando la cuenta en el mismo paso.

**Arquitectura:** Next 15 con App Router. Lo público —búsqueda y perfil— se
renderiza en el servidor para que Google lo indexe; lo privado —reservar,
registro, mis turnos— sale directo del browser con la cookie de sesión. La línea
cae donde cae la autenticación, así que nunca hay que reenviar una cookie.

**Stack:** Next 15, TypeScript, pnpm workspaces, Tailwind, shadcn/ui sobre
Radix, `openapi-typescript` para los tipos, Playwright para un E2E.

**Spec:** [2026-08-30-apps-web-design.md](../specs/2026-08-30-apps-web-design.md)
**Base:** rama `refactor-gian`, commit `7a4b910`

## Restricciones globales

Aplican a **todas** las tareas.

- **Español en todo lo que se escribe:** componentes, funciones, variables,
  props, rutas y copy. Quedan en inglés las palabras del framework (`page`,
  `layout`, `loading`) y las de la plataforma (`fetch`, `useState`).
- **Sin gestor de estado global. Sin librería de formularios. Sin cliente de API
  generado.** Se generan los *tipos*, no el cliente.
- **Los tipos salen de `apps/api/api/openapi.yaml`.** Ningún tipo de respuesta se
  escribe a mano.
- **El acento (`--color-accion`) aparece solo en la acción principal de cada
  pantalla.** En ningún otro lado.
- **Ningún gris puro.** Todos los neutros llevan sesgo hacia el índigo.
- **El color nunca es la única señal.** Un estado se distingue además por forma,
  texto o borde.
- **4.5:1 de contraste como piso** para todo texto.
- **El motivo de consulta no aparece nunca** en listados, previsualizaciones ni
  en ningún `<title>`. Ley 25.326.
- **Nada de datos inventados.** Sin fotos, sin rating, sin reseñas: la API no
  los tiene y el front no los finge.
- Todos los comandos se corren desde la raíz del repo salvo que se diga otra cosa.

- [ ] **Paso 6: implementar el formato**

`apps/web/lib/formato.ts`:

```ts
// La API manda todo en la zona horaria de Argentina y los montos en centavos.
// Estas tres funciones son el único lugar donde eso se traduce a algo legible:
// formatear inline en cada pantalla es cómo aparecen los precios con dos
// órdenes de magnitud de diferencia.

const ZONA = "America/Argentina/Buenos_Aires";

export function formatearPrecio(centavos: number): string {
  const pesos = centavos / 100;
  const tieneCentavos = centavos % 100 !== 0;
  return new Intl.NumberFormat("es-AR", {
    style: "currency",
    currency: "ARS",
    minimumFractionDigits: tieneCentavos ? 2 : 0,
    maximumFractionDigits: tieneCentavos ? 2 : 0,
  })
    .format(pesos)
    .replace(/\s/g, "");
}

export function formatearHora(iso: string): string {
  return new Intl.DateTimeFormat("es-AR", {
    hour: "2-digit",
    minute: "2-digit",
    hour12: false,
    timeZone: ZONA,
  }).format(new Date(iso));
}

export function formatearDia(iso: string): string {
  return new Intl.DateTimeFormat("es-AR", {
    weekday: "long",
    day: "numeric",
    month: "long",
    timeZone: ZONA,
  }).format(new Date(iso));
}
```

```ts
import type { components } from "./contrato";

type Esquemas = components["schemas"];

export type Profesional = Esquemas["Profesional"];
export type ListaProfesionales = Esquemas["ListaProfesionales"];
export type Hueco = Esquemas["Hueco"];
export type ListaHuecos = Esquemas["ListaHuecos"];
export type Turno = Esquemas["Turno"];
export type ListaTurnos = Esquemas["ListaTurnos"];
export type Problema = Esquemas["Problema"];

const BASE = process.env.NEXT_PUBLIC_API_URL ?? "http://localhost:8080";

// ErrorAPI conserva el estado HTTP además del mensaje. La pantalla de reserva
// muestra cosas distintas ante un 409 y un 422, y sin el número no puede
// distinguirlos.
export class ErrorAPI extends Error {
  constructor(
    readonly estado: number,
    readonly problema: Problema,
  ) {
    super(problema.detail ?? problema.title);
    this.name = "ErrorAPI";
  }
}

// pedir es todo el cliente. No hay capa de recursos ni cliente generado: son
// cientos de líneas para envolver fetch, y el contrato ya da los tipos.
export async function pedir<T>(ruta: string, opciones: RequestInit = {}): Promise<T> {
  const respuesta = await fetch(`${BASE}${ruta}`, {
    ...opciones,
    // Sin esto la cookie de sesión no viaja: el front y la API están en
    // orígenes distintos, y por eso existe el middleware CORS del back.
    credentials: "include",
    headers: {
      // La API responde 415 a cualquier cuerpo que no llegue como JSON. Es
      // parte de su defensa contra CSRF, no una formalidad.
      ...(opciones.body ? { "Content-Type": "application/json" } : {}),
      ...opciones.headers,
    },
  });

  if (respuesta.status === 204) {
    return undefined as T;
  }

  const cuerpo = await respuesta.json();
  if (!respuesta.ok) {
    throw new ErrorAPI(respuesta.status, cuerpo as Problema);
  }
  return cuerpo as T;
}
```

- [ ] **Paso 1: el buscador del próximo hueco**

`apps/web/lib/huecos.ts`:

```ts
import { pedir, type Hueco, type ListaHuecos } from "./api";

// Siete días, no el horizonte completo. GET /huecos exige un rango y devuelve
// todos los del período: pedir sesenta días para mostrar uno solo son cincuenta
// huecos de JSON por profesional, multiplicado por los resultados de la página.
const DIAS_DE_VENTANA = 7;

function comoFecha(d: Date): string {
  return d.toISOString().slice(0, 10);
}

// ponytail: esto es un N+1 contra la API. El listado no devuelve huecos, así
// que hay una llamada por resultado. El arreglo real es un campo
// proximoDisponible calculado en el back, y es una etapa chica: se hace cuando
// el listado se sienta lento o cuando exista PostgreSQL, lo que llegue primero.
export async function proximoHueco(profesionalID: string): Promise<Hueco | null> {
  const hoy = new Date();
  const hasta = new Date(hoy);
  hasta.setDate(hoy.getDate() + DIAS_DE_VENTANA);

  try {
    const respuesta = await pedir<ListaHuecos>(
      `/api/v1/profesionales/${profesionalID}/huecos` +
        `?desde=${comoFecha(hoy)}&hasta=${comoFecha(hasta)}`,
    );
    // Vienen ordenados por inicio desde el servidor.
    return respuesta.datos[0] ?? null;
  } catch {
    // Un profesional que todavía no cargó su horario no es un error de la
    // búsqueda: es una tarjeta sin horarios. Que un fallo suyo rompa el
    // listado entero sería peor que no mostrar su disponibilidad.
    return null;
  }
}
```

## Task 5: `/perfiles/[slug]` perfil público

La pantalla que indexa Google. Es la razón por la que el front es Next.

**Archivos:**
- Crear: `apps/web/app/perfiles/[slug]/page.tsx`

**Interfaces:**
- Consume: `pedir`, `Profesional`, `ListaHuecos`, `Hora`, `formatearPrecio`,
  `formatearDia`

- [ ] **Paso 1: la página con sus metadatos**

```tsx
import type { Metadata } from "next";
import { notFound } from "next/navigation";
import { ErrorAPI, pedir, type Profesional } from "@/lib/api";

const ESPECIALIDADES: Record<string, string> = {
  psicologia: "Psicología",
  kinesiologia: "Kinesiología",
  odontologia: "Odontología",
};

async function traerPerfil(slug: string): Promise<Profesional> {
  try {
    return await pedir<Profesional>(`/api/v1/perfiles/${slug}`);
  } catch (e) {
    if (e instanceof ErrorAPI && e.estado === 404) notFound();
    throw e;
  }
}

// Estos metadatos son el producto de haber elegido Next. Un perfil sin title ni
// description propios no se distingue de ningún otro en un resultado de
// búsqueda, que es el canal por el que llegan los pacientes.
export async function generateMetadata({
  params,
}: {
  params: Promise<{ slug: string }>;
}): Promise<Metadata> {
  const { slug } = await params;
  const p = await traerPerfil(slug);
  const especialidad = ESPECIALIDADES[p.especialidad] ?? p.especialidad;

  return {
    title: `${p.nombre} ${p.apellido} — ${especialidad} en ${p.zona}`,
    description: p.bio.slice(0, 155),
    alternates: { canonical: `/perfiles/${slug}` },
  };
}
```

> **Por qué la especialidad sí puede ir en el `<title>` acá.** La regla de la
> spec es que no aparezca en *notificaciones*: un mensaje que diga "tu turno de
> Psicología" filtra un dato de salud del paciente a la pantalla bloqueada de su
> teléfono. Acá la especialidad es del **profesional**, es información que él
> publica, y es lo que hace que la página se encuentre. No es el mismo dato.

## Task 6: `/perfiles/[slug]/reservar`

La pantalla con el diseño de verdad. Es de cliente: crea cuenta y reserva.

**Archivos:**
- Crear: `apps/web/app/perfiles/[slug]/reservar/page.tsx`

**Interfaces:**
- Consume: `pedir`, `ErrorAPI`, `Turno`, `Hueco`, `Hora`

- [ ] **Paso 1: la estructura de la pantalla**

Tres estados en una sola página, sin router entre ellos:

1. **Elegir** — los huecos del profesional. Si vino `?inicio=` en la URL, ese
   arranca elegido.
2. **Confirmar** — el resumen del turno y el formulario: email, contraseña,
   nombre, apellido y motivo opcional.
3. **Listo** — el turno reservado, con link a `/turnos`.

- [ ] **Paso 2: las dos llamadas**

```tsx
async function reservar(datos: DatosFormulario) {
  setEnviando(true);
  setError(null);

  try {
    // 1. Registrarse. El back deja la sesión abierta en la misma respuesta,
    //    así que no hace falta un login después.
    await pedir("/api/v1/usuarios", {
      method: "POST",
      body: JSON.stringify({
        email: datos.email,
        contrasena: datos.contrasena,
        nombre: datos.nombre,
        apellido: datos.apellido,
      }),
    });
  } catch (e) {
    if (e instanceof ErrorAPI && e.estado === 409) {
      // El caso más probable de los dos: alguien que ya se registró antes y no
      // se acuerda. Un link, no un login en línea: conservar el hueco a través
      // de un segundo flujo son ochenta líneas para ahorrar dos clicks.
      setError({
        mensaje: "Ya tenés una cuenta con ese email.",
        accion: { texto: "Entrar", href: `/entrar?volver=${encodeURIComponent(rutaActual)}` },
      });
      setEnviando(false);
      return;
    }
    throw e;
  }

  try {
    // 2. Reservar. Ya hay sesión.
    const turno = await pedir<Turno>(`/api/v1/profesionales/${profesionalID}/turnos`, {
      method: "POST",
      body: JSON.stringify({ inicio: elegido.inicio, motivo: datos.motivo }),
    });
    setPaso("listo");
    setTurno(turno);
  } catch (e) {
    if (e instanceof ErrorAPI && e.estado === 409) {
      // Alguien tomó el hueco mientras completaba el formulario. La cuenta ya
      // existe y la sesión está abierta, así que volver a elegir es un click:
      // no se pierde nada de lo que hizo.
      await recargarHuecos();
      setElegido(null);
      setPaso("elegir");
      setError({ mensaje: "Ese horario se tomó recién. Elegí otro." });
      setEnviando(false);
      return;
    }
    throw e;
  }
}
```

- [ ] **Paso 3: los errores de validación**

Un 422 trae `errores: [{campo, mensaje}]`. Cada mensaje va **debajo de su
campo**, no en un cartel arriba: un error de formulario que no está al lado del
campo obliga a buscar cuál falló.

El campo con error lleva `aria-invalid` y su mensaje se enlaza con
`aria-describedby`, o un lector de pantalla anuncia el input sin decir qué está
mal.

| Contraseña de 5 caracteres | 422 con el mensaje debajo del campo de contraseña |

empieza en tu dominio:

```tsx
function destinoSeguro(volver: string | null): string {
  // Tiene que empezar con una sola barra: "//otro-sitio.com" es una URL
  // absoluta con protocolo relativo y el browser la sigue igual.
  if (!volver || !volver.startsWith("/") || volver.startsWith("//")) {
    return "/turnos";
  }
  return volver;
}
```

## Notas de riesgo

**Ninguna tarea toca `apps/api`.** Es la primera etapa puramente aditiva del
proyecto: nada de lo que existe puede romperse. El riesgo cambió de lugar.

**El riesgo real es el criterio 2.** Es fácil escribir una pantalla que se ve
perfecta y que resulta ser un Client Component — basta un `useState` mal puesto,
o un componente hijo con `"use client"` que arrastra al padre. Todo funciona
igual en el browser y el SEO desaparece sin que nada falle. Por eso el paso 2 de
la Task 10 se hace apagando JavaScript en el browser, no leyendo el código.

**El segundo riesgo es el N+1 de la Task 4.** Está anotado y es deliberado, pero
crece linealmente con los resultados por página. Si el listado empieza a
sentirse lento antes de que exista PostgreSQL, la respuesta no es cachear del
lado del front: es el campo `proximoDisponible` en el back.

**Lo que esta etapa deja sin cerrar:** no hay fotos ni reseñas, y el perfil se ve
más vacío que el prototipo por eso. Es honesto —la API no los tiene y el front
no los inventa— pero es la diferencia más visible entre lo que ya viste y lo que
vas a ver.
